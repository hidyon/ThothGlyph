# テスト仕様

> **更新のタイミング**: 検証の手段や分担が変わったとき、テストの本数が変わったとき。
> issueをクローズしたら、件数と一覧を実際の出力に合わせる。

## 1. 何をどちらで確かめるか

3つの手段がある。**どれで確かめるかは、issue仕様の受け入れ基準を書くときに
項目ごとに決める。**

| 手段 | コマンド | 守る範囲 | 向くもの |
|---|---|---|---|
| 単体テスト（Vitest） | `npm test` | `src/lib/` の純粋関数 | 入出力の網羅、エッジケース、回帰の固定 |
| 実機検証（ヘッドレスChromium） | `node scripts/verify-ui.mjs` | 画面と操作の往復 | 描画、入力、保存、レイアウト、描画の性能 |
| 読み込みの実測（本番ビルド） | `node scripts/measure-load.mjs` | 成果物の大きさと初期表示までの時間 | バンドルの分割、読み込みの性能 |

**読み込みの時間は `verify-ui.mjs` では測らない。** 開発サーバはバンドルされて
いないので、測っても本番の値にならない（[0024](specs/0024-bundle-size.md)）。

**型が通ることは検証ではない。** `npm run build`（`tsc -b` + vite build）と
`npm run lint`（oxlint）は前提であって、受け入れ基準の確認ではない。
その型チェックは `strict` で走る（[0026](specs/0026-typescript-strict.md)）ので、
前提の強さは `strict` の範囲まで。そこから先は上の3つで確かめる。

境界の引き方: 文字列を入れて文字列が返るものはテスト、DOMに出て初めて確かめられる
ものは実機。`renderMarkdown` の出力は文字列なのでテスト、その文字列が
ブラウザでどう見えるかは実機。

## 2. 単体テスト

### 置き場所と書き方

対象の隣に `*.test.ts` として置く（`src/lib/renderMarkdown.test.ts`）。
`tests/` ディレクトリは切らない。`it()` の説明は日本語で「何が起きるか」を書く。

環境は既定の node。ただし `renderMarkdown.test.ts` だけは jsdom で動かす
（DOMPurifyの `sanitize` が `window` を要求するため、ファイル先頭に
`// @vitest-environment jsdom`）。`documentStorage.test.ts` は `window.localStorage` を
スタブする（差し替えるのは `getItem` / `setItem` / `removeItem` の3つだけ。
`removeItem` は0065の読み継ぎが旧キーを消すため）。
`langStorage.test.ts` は `navigator.language` もスタブする（既定の言語が
実行環境で変わると結果が変わるため）。

### 既知の不具合の書き方

直せない・直さない不具合は `it.fails()` で「いま失敗すること」を書き残す。
直したときに `it()` へ裏返す。放置された不具合が一覧に見えるようにするため。
[0006](specs/0006-math-in-code.md) はこの形で引き継いだ（0014で2件記録 → 0006で裏返し）。

## 3. 実機検証

### 手順

```bash
npm run dev                  # 別ターミナルで起動しておく
node scripts/verify-ui.mjs   # 既定区分。画面幅を除く。スクリーンショットは tmp/screenshots/ に出る
node scripts/verify-ui.mjs width   # 画面幅区分だけ
node scripts/verify-ui.mjs theme        # テーマ区分だけ
node scripts/verify-ui.mjs theme perf   # 複数指定
```

**区分を選んで流せる**（[0017](specs/0017-verify-script-structure.md)）。
引数なしなら既定区分だけを実行する。画面幅の確認は `width` を指定して実行する。知らない名前を渡した場合は
使える名前を出して終了コード1で終わり、チェックは1件も実行しない。

区分はどれから流しても同じ結果になるよう、実行前に毎回初期状態へ戻す
（保存された文書とテーマを消し、OSのテーマ設定と画面幅を既定に戻す）。
**表示言語は日本語に固定して流す。** 既存のチェックの多くが日本語の文言で要素を
探しており、ヘッドレスChromiumの `navigator.language` は英語なので、放っておくと
英語で表示されて全部落ちる。固定は `addInitScript` で、保存がないときだけ
`ja` を置く形にしてある（`i18n` 区分が英語を保存したら、そちらが優先される）。
消す前に保存のデバウンス待ちを片付けるのは、保存が飛んだままリロードすると
`beforeunload` で書き戻されるため。

Chromiumはコンテナに焼いてあるので準備は要らない。`chromium.launch()` に
`executablePath` は**書かない**（`PLAYWRIGHT_BROWSERS_PATH` から
playwright-coreが自力で見つける。パスをベタ書きすると環境が変わった瞬間に嘘になる）。

### スクリプトの形

- 受け入れ基準は**1項目1チェック**で足し、`OK` / `NG` と「n/m 件」を出す。
- 1件でも落ちたら終了コードを1にする。コンソールエラーがあっても1にする。
- **前回までのissueのチェックは消さない。** 回帰に気づけなくなる。
- スクリーンショットは撮るだけでなく**実際に見る**。見た目の違和感は目視で
  判断せず、DOMの座標や値を測って確かめる（`aligned` の桁揃えは目の錯覚で
  崩れて見えることがある）。
- **画像も目視で判定しない。** アイコンが16pxで潰れていないかは、canvasに
  描いてインク量を数える（[0019](specs/0019-app-icon.md)）。ただし
  **faviconがタブにどう出るかはページのDOMの外**なので機械では見られない。
  そこは手元のブラウザで見る、と決めて仕様に書く。

### file:// で開ける出力の検証（[0074](specs/0074-file-protocol.md)）

`node scripts/verify-file-build.mjs`（`--skip-build` で既存の `dist-file` を確かめる）。
**14件**・約25秒。`npm run build:file` を流してから、`file://` で開いて確かめる。

| 見るもの | 内容 |
|---|---|
| 出力の形 | `index.html` と `app.js` ができていること、script タグに `type="module"` と `crossorigin` が無く `defer` が付いていること |
| 読み込み | 取れなかったファイルが0件、コンソールエラーが0件 |
| 描画 | エディタが出る、数式17個（0078で参照の文を足して増えた）、グラフ1つ、パレットのボタン、KaTeXのフォントが当たっている、ツールバーのロゴが描かれている |
| 操作 | パレットのボタンを押すと挿入される |
| 保存 | リロードで残る、**別のフォルダへコピーして開いても出る**（`file://` は保存を共有する） |
| 速さ | 数式が出るまで1秒以内（実測692ms。ローカルディスクなので回線の影響を受けない） |

**`verify-ui.mjs` の494件はこちらに持ってこない。** ここで見るのは
「`file://` で成り立つか」だけで、画面の振る舞いは重複させない。

### 落ちたときに何が残るか

[0027](specs/0027-verify-flaky.md) で入れた。

- **落ちたチェックは末尾に再掲する。** 区分名・ラベル・実測値つき。スクロールで
  流れても末尾だけ見れば分かる。全件OKならこの節は出ない。
- **結果は `tmp/verify-result.json` にも書く。** 出力を切ってしまっても後から読める
  （出力先は環境変数 `VERIFY_JSON` で変えられる）。
- **タイミングに依存するチェックには `⏱` が付く**（JSONでは `"timing": true`）。
  現在6件。「落ちてもよい」ではなく、**落ちたときに疑う順番**を示す印で、
  判定そのものは印の有無で変わらない。
- **時間で消える表示を見るチェックは、読む前に出るのを待つ**（`waitForFunction`）。
  コピーや読み込みの結果は数秒で消えるので、待たずに読むと空文字と比べて揺れる
  （0033で足したチェックが実際に揺れた）。
- **`--repeat N` で繰り返して揺れを見る。** 回ごとに結果が割れたチェックだけを
  目立たせる。1回でも落ちれば終了コードは1。

```bash
node scripts/verify-ui.mjs --repeat 5 perf
```

**出力を `tail` などで切り詰めない。** 件数だけが残っても、フレークと本物の
回帰を区別できない（実際に1度、42/43で落ちた実行の中身を取り逃がしている）。

### READMEのスクリーンショット（[0035](specs/0035-readme-for-users.md)）

`node scripts/make-screenshots.mjs` で `docs/screenshots/` の2枚
（1440×900と360×667のダークテーマ）を撮り直す。
条件（localStorageを消した初期表示、サンプル文書、数式とパレットの描画待ち）を
スクリプトが揃えるので、手で撮らない。**画面の見た目を変えたissueでは撮り直す。**

### 色の測り方

配色は目で見て決めない。`getComputedStyle` から文字色と背景色を取り、
WCAGの相対輝度でコントラスト比を計算して4.5:1以上を確かめる
（スクリプトの `contrastOf`）。初期表示のちらつきは、`waitUntil: 'commit'` で
読み込み直後から背景色を繰り返し読み、意図しない色が現れないことで見る。

### 性能の測り方

400節・400数式の文書をスクリプトが生成し、20文字を連続入力して
「1文字あたりの入力反映」と「入力停止からプレビューが追いつくまで」を測る。
自動保存が動く状態のまま測る（保存のコストも体感に効くため）。

直近の実測（2026-09-21、`--repeat 5` の幅）: **35.8〜40.2ms/文字**（基準50ms以内）、
**282〜1497ms**（基準1.5秒以内）。実装前は約1200ms/文字だった。

**0010の前後で測り直した結果、1文字あたり約6ms増えている**
（前 31.6〜34.1ms → 後 35.8〜40.2ms）。`data-line` のぶんサニタイズと
DOMへの反映が増えるため。どちらも基準内だが、**追いつくまでの時間は
最悪値が1497msで基準の1.5秒に余裕がない**（[0059](issues/0059-perf-headroom.md)）。

> ここに前から書いてあった「29.2ms/文字・300〜500ms」は、測った環境が違う
> 古い値だった。**性能の数値を引き継ぐときは測り直す。**

### 読み込みの測り方（`scripts/measure-load.mjs`）

`npm run build` → `vite preview` で配る → ヘッドレスChromiumで2条件×3回開く、まで
スクリプトが自分でやる。測るのは **textareaが出るまで / プレビューに数式が出るまで /
パレットのラベルがKaTeXで描画されるまで**の3つで、中央値を取る。
成果物の大きさ（初期JS・遅延JS・初期CSS、gzip込み）と、遅延チャンクにKaTeX・marked・
DOMPurifyが入っていること（初期チャンクに入っていないこと）も同じスクリプトで見る。

スロットルの条件は Chrome DevTools の Fast 3G 相当（下り1.6Mbps・上り750kbps・
RTT 150ms）とCPU 4倍遅く、で固定する。**条件を変えると過去の数値と比べられない。**

直近の実測（[0024](specs/0024-bundle-size.md) の実装後）:

| | 初期JS | Fast 3G + CPU 4倍 textareaまで | 同 数式まで |
|---|---|---|---|
| 分割前 | 579.98 kB（gzip 180.50） | 1964 ms | 2021 ms |
| 分割後 | 243.20 kB（gzip 76.82） | 1085 ms | 1939 ms |
| 0079の後 | 272.20 kB（gzip 85.86） | 1079 ms | 2252 ms |

**0079の時点で12件中2件が落ちている。** 初期CSSが12.00 kB（基準10 kB。
[0073](issues/0073-initial-css-size.md)）と、スロットルなしのtextareaまでが
253〜322 ms（基準250 ms。[0081](issues/0081-load-headroom.md)）。
どちらも要求仕様N10（Fast 3G + CPU 4倍で1500 ms・初期JS 300 kB以下）は満たしている。

結果は `tmp/measure-load.json` にも書く。1件でも基準を外れたら終了コード1。

## 4. テストを足すときの指針

- **不具合を直すときは、まず失敗するテストを書く。** 直ってから書くと、
  そのテストが本当に不具合を捕まえるか分からない。
- **性能のissueは、起票の時点で現状を実測して数値を残す。** 「速くなった気がする」で
  終わらせない。
- 受け入れ基準は**外から観測できる結果**で書く。「保存しない」ではなく
  「保存状態の表示が出ない」。内部状態で書くと、実装を変えたときに基準ごと嘘になる。
- 落ちているテストを消して通すのは、直したことにならない。直せないなら
  `it.fails()` に変えて理由をissueに書く。
