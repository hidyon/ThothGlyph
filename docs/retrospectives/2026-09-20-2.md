## 仕様が実装中に変わった箇所

### 0033: 測ったのが「画面の状態1つだけ」だった

未確認の前提に「保存状態が出ているときは測っていない」と書いていて、実際に崩れた。
**英語・幅360pxで2px溢れた**。仕様の表（320pxまで収まる）は
**保存状態が空の初期表示**で測った数字だった。

`gap` と `padding` を詰めて360pxまで収め、約束する幅を320px→360pxへ直した。
ここは「測ったのに漏れた」例で、漏れたのは**測る幅**ではなく**測る状態**である。
画面の要素は、状態によって最も大きくなるとき（保存状態あり、長い文言、英語）が
別にある。

→ **提案1**: 測るルールに「その要素がいちばん大きくなる状態で測る」を足す。

### 0034: 自分が書いた仕様の中で規則が食い違っていた

ファイル名の規則に「使えない文字（`/ \ : * ? " < > |`）を `-` に置き換える」と
「記法は剥がさないので `*` が残るのは許容する」を**両方**書いていた。
`*` は置き換え対象なので、`# **強調**` は `--強調--.md` になる。
単体テストを書いた時点（実装直後）で落ちて気づいた。

仕様の外との食い違い（前提の崩れ）はこれまで何度も扱ってきたが、
**仕様の内側での食い違い**は初めて記録する。原因ははっきりしていて、
規則を**文だけで書き、例を1つも書かなかった**こと。
`# **強調**` → `?` を仕様に書こうとしていれば、書いた時点で答えが出ない
ことに気づけた。

もう1つ、規則が拾えていない入力もあった（`# ///` → `---`。中身のない名前）。
これも例を並べていれば出てきた種類のものである。

→ **提案2**: 仕様に変換規則を書いたら、入力と出力の例を仕様の中に並べる。

### 0012: CSSの詳細度で見出し行が3px高くなった

`.button--small` を `.button` と同じ詳細度で書いたため、幅720px以下の
`.button`（`padding: 7px 12px`）に後ろから上書きされ、見出し行が30px→33px、
textareaが207px→204pxになった。検証で落ちて、`.button.button--small` に直した。

これは**受け入れ基準が捕まえた**例。「幅375pxでtextareaが207px以上」を
基準に入れていたので、3pxの差が自動で落ちた。0032・0033で守ってきた数字を
**次のissueの基準にも引き継いだ**ことが効いている。

### 0034: ボタンの並びが散らばった（基準になかった）

見出し行に2つ目のボタンを足したら、`space-between` で3要素が均等配置になり、
「ファイルに保存」が中央に浮いた。**スクリーンショットの目視で見つけた**。
受け入れ基準には高さ・幅・溢れの数値しかなく、並びの見た目は入っていなかった。

ここは数値の基準を増やすより、**UIの変更はスクリーンショットを見る**という
既存のルール（CLAUDE.mdの検証フェーズ）が働いた場面として記録しておく。

## 受け入れ基準で捕まえられなかった問題

### 書き間違いで開発サーバが500を返し、検証がタイムアウトした（0012）

JSXの属性の閉じ引用符を落としたまま検証を流した。Viteが500を返し、
検証は「`.preview .katex` が出ない」で30秒待って落ちた。
**症状（要素が出ない）と原因（構文エラー）が遠く**、`curl` で開発サーバの応答を
見るまで分からなかった。型チェックも通ってしまっていた。

`npm run build` を先に流していれば1秒で分かった。

→ **提案3**: 実装を書き換えたら、検証スクリプトを流す前にビルドを通す。

### 自分で足したチェックが揺れた（0033）

「コピー結果が出る」のチェックで、表示が出る前に読みに行っていた。
1回目の全区分で落ち、`waitForFunction` で待ちを入れて直した。
0027で「揺れ」を扱ったのに、**新しく足すチェックで同じ種類を作った**。

これはCLAUDE.mdではなく [test-spec.md](../test-spec.md) 側の話なので、
同文書の「検証スクリプトの書き方」に1行足すのが適切だと考える
（時間で消える表示を見るチェックは、読む前に出るのを待つ）。
