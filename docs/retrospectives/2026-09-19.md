## 仕様が実装中に変わった箇所

3件のうち2件で、仕様に書いた前提が実装で崩れた。いずれも**実際に動かす前に
決め打ちした技術的前提**だった。

1. **0014**: 「`localStorage` のスタブで足りるのでjsdomは入れない」と書いたが、
   DOMPurifyの `sanitize` が `window` を要求し、node環境では動かなかった。
   → jsdomを足した。
2. **0006**: フェンスの判定を正規表現で書く前提だったが、複数行モードの `$` が
   行末にも当たるため「閉じないフェンスは末尾まで」が表せなかった。
   → 行単位の走査に変えた。
3. **0001**: 「初回レンダリングか」で初回保存を抑止する実装が、React StrictModeの
   二重マウントで破れた。→ 最後に保存した内容との比較に変えた。

**なぜ仕様の時点で気づけなかったか。** 3つとも「ライブラリや環境が実際にどう動くか」

**提案**: 仕様に「確かめずに書いた前提」を明示する節を設ける。書いた時点で未確認の
ものは断定せず、実装の最初にそこから確かめる。CLAUDE.mdの仕様テンプレートに
`## 未確認の前提` を足したい。

## 受け入れ基準で捕まえられなかった問題

- **0001の受け入れ基準は全部通ったのに、初回訪問時にサンプルが保存される不具合が
  残っていた。** 検証スクリプトを書いて初めて気づいた。基準に「初回訪問では
  保存状態を出さない」を入れていたのが効いた——が、これは仕様を書くときに
  「保存しない」という**内部の状態**ではなく「表示が出ない」という**観測できる結果**で
  書いたから捕まえられた。内部状態で書いていたら通り抜けていた。
- 0007では受け入れ基準に**数値**（50ms以内、1.5秒以内）を入れた。実測29.2msと308msで、
  「速くなった気がする」で終わらずに済んだ。起票時に現状を実測してあったことが効いた。

**提案**: 「受け入れ基準は観測できる結果で書く」「性能の話は起票の時点で現状を測る」の
2つをCLAUDE.mdの仕様の節に足したい。

「確認する」を禁じるだけでなく**確かめ方そのものを設計させる**方向に働いた。

実際、書いたおかげで一歩踏み込めた。エラーが出ることだけでなく、
`--strict false` にすると同じコードが0件で通ることまで確かめ、
**止めているのが `strict` であって他のフラグではない**ことを記録できた。

## 削るべきルール

### 「issueを3件クローズするごとに振り返る」の3件

実績は 4件 → 2件 → 1件 → 2件。**一度も3件で回っていない。**
3回目に「数え方を徹底すればよい」と結論したが、今回も2件で実施している
（ユーザーの指示による）。

守られない数字を掲げ続けると、ルール全体の重みが下がる。実態を見ると、
振り返りが起きているのは「区切りがついたとき」か「進め方に引っかかりが出たとき」で、
件数ではない。今回も、検証の揺れという引っかかりがあった直後である。

→ **提案**: 「3件クローズするごとに」を
「**issueを2〜3件クローズしたとき、または進め方に引っかかりが出たとき**」に緩める。

CLAUDE.mdは足すだけでなく減らす、の観点では、**数字を1つ手放す**提案になる。

## 仕様が実装中に変わった箇所

### `CURSOR_TOKEN` の置き方（0018）

仕様には「解の公式なら `x` の位置に置く」と書き、記号を**置き換える**形を
想定していた。実装中に、置き換えるとトークンを取り除いた文字列が壊れる場合が
あることに気づいた。

```
%CURSOR%^2 = a^2 + b^2 - 2ab \cos C   →  トークンを消すと ^2 = … で壊れる
```

**直前に置く**形に変えた。トークンを消した文字列が常に元の式のままになる。

なぜ仕様の時点で気づけなかったか。仕様を書くとき、解の公式（`x = …`）だけを
見て決めていた。30件のうち1件で成り立つ置き方を、全体の規則として書いていた。
**データを1件だけ見て規則を決めると、残りで破れる。**

→ 大きな損はなかった（実装中に気づき、方針を変えただけ）。ただし
「代表例1つで規則を決めない」は、次に同じ形のissue（データを並べるもの。
[0011](../issues/0011-palette-search.md) や収録範囲を増やす類）で効くはず。
ルールにするほどではないが、覚えておく。
