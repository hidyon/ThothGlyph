# 振り返り 2026-09-19

対象: [0001](../issues/0001-autosave.md) 自動保存、[0014](../issues/0014-unit-tests.md)
テスト土台、[0006](../issues/0006-math-in-code.md) コード内の `$`、
[0007](../issues/0007-preview-performance.md) プレビュー性能。
振り返るのはコードではなく進め方。

## 仕様が実装中に変わった箇所

3件のうち2件で、仕様に書いた前提が実装で崩れた。いずれも**実際に動かす前に
決め打ちした技術的前提**だった。

1. **0014**: 「`localStorage` のスタブで足りるのでjsdomは入れない」と書いたが、
   DOMPurifyの `sanitize` が `window` を要求し、node環境では動かなかった。
   → jsdomを足した。
2. **0006**: フェンスの判定を正規表現で書く前提だったが、複数行モードの `$` が
   行末にも当たるため「閉じないフェンスは末尾まで」が表せなかった。
   → 行単位の走査に変えた。
3. **0001**: 「初回レンダリングか」で初回保存を抑止する実装が、React StrictModeの
   二重マウントで破れた。→ 最後に保存した内容との比較に変えた。

**なぜ仕様の時点で気づけなかったか。** 3つとも「ライブラリや環境が実際にどう動くか」
であって、考えれば分かる類ではない。1行動かせば分かることを、仕様に断定で書いていた。

**提案**: 仕様に「確かめずに書いた前提」を明示する節を設ける。書いた時点で未確認の
ものは断定せず、実装の最初にそこから確かめる。CLAUDE.mdの仕様テンプレートに
`## 未確認の前提` を足したい。

## 受け入れ基準で捕まえられなかった問題

- **0001の受け入れ基準は全部通ったのに、初回訪問時にサンプルが保存される不具合が
  残っていた。** 検証スクリプトを書いて初めて気づいた。基準に「初回訪問では
  保存状態を出さない」を入れていたのが効いた——が、これは仕様を書くときに
  「保存しない」という**内部の状態**ではなく「表示が出ない」という**観測できる結果**で
  書いたから捕まえられた。内部状態で書いていたら通り抜けていた。
- 0007では受け入れ基準に**数値**（50ms以内、1.5秒以内）を入れた。実測29.2msと308msで、
  「速くなった気がする」で終わらずに済んだ。起票時に現状を実測してあったことが効いた。

**提案**: 「受け入れ基準は観測できる結果で書く」「性能の話は起票の時点で現状を測る」の
2つをCLAUDE.mdの仕様の節に足したい。

## 守られなかったルール / 明文化したい暗黙のルール

- **守られなかった**: 「issue着手時に `issue/NNNN-slug` ブランチを切る。`main` に
  直接コミットしない」は守れたが、**完了したブランチをどうするかが書かれていない**。
  0001をmainへマージしようとして権限で拒否され、0014のブランチを0001の上に積んだ。
  結果、4本のブランチが直列に伸びている。
  → マージの扱い（誰がいつやるか）をCLAUDE.mdに書きたい。
- **暗黙にやっていた**: 実装中に見つけた別の問題をissueにすること。今回は
  `insertSnippet` が既に選択範囲を包んでいた（0009の前提が誤り）ことが分かり、
  issueを書き直した。CLAUDE.mdには「新しいissueとして起票する」とあるが、
  「既存issueの前提が誤っていたら書き直す」は書かれていない。小さいので
  ルールを足すほどではないかもしれない。
- **暗黙にやっていた**: 検証スクリプトに受け入れ基準を1項目1チェックで足し、
  `OK/NG` と件数を出す形。0001で作ってから0006・0007でもそのまま使えた。
  CLAUDE.mdの「実機検証」に、この形を標準として書いておきたい。

## 削るべきルール

- CLAUDE.mdの構成図（`src/` のツリー）は、ファイルが増えるたびに更新が要る。
  今回2回更新した。`lib/` の中身は実際に見れば分かるので、**ツリーは
  ディレクトリの役割だけに減らせる**と思う。長いほど読まれなくなる。
- 「`@types/katex` は入れない」「Viteの `server.host` は消さない」は、どちらも
  一度踏んだ落とし穴の記録として今も有効。残す。

## CLAUDE.mdへの変更提案（2026-09-19 承認・適用済み）

1. 仕様テンプレートに `## 未確認の前提` を足す。
2. 「受け入れ基準は観測できる結果で書く」「性能は起票時に現状を測る」を追記。
3. 完了したissueブランチのマージの扱いを書く。
4. 実機検証の節に、`OK/NG` と件数を出す検証スクリプトの形を標準として書く。
5. `src/` のツリーを、ファイル単位からディレクトリの役割に減らす。

5点とも承認され、同日 `docs/claude-md-revision` で適用した。

書く手間はあったが、**アーキテクチャ文書に「`index.html` が唯一の例外」と

# 振り返り（3回目） 2026-09-19

対象: [0009](../issues/0009-wrap-selection.md) 選択範囲があるときの挿入。
あわせて、issueを3件起票したとき（0018・0019・0020）の進め方も見る。

## 数え方を間違えた

まず前提の訂正から。クローズ報告のときに「0002・0016に続く3件目のクローズ」と
言ったが、これは誤りだった。2回目の振り返りが0016と0002を対象にしているので、
**そこから数えれば0009は1件目**である。

CLAUDE.mdの「3件クローズするごとに」を守るなら、振り返りはまだ先だった。
1回目が4件、2回目が2件、3回目が1件。一度も「3件ごと」で回っていない。
数字が守られていないこと自体より、**毎回わたしが数え違えていること**が問題で、
数え始める起点（前回の振り返りの対象はどこまでか）が記録から読み取りにくい。

→ 各振り返りの冒頭に「対象」を書く運用は既にできている。数える起点はそこなので、
ルールを変えるより**振り返りを書く前に前回の「対象」を読む**を徹底すればよい。
今回それをやって気づいた。ルールの追加は要らないと判断する。

## 前回の変更は効いたか

### 受け入れ基準の動詞を「残るもの」で書く — 効いた

0009の受け入れ基準12項目に、「確認する」「報告する」で終わるものは1つもない。
すべて具体的な入出力か、DOMから読める値になっている
（`insertSnippet('x + 1', '\pi', 0, 5)` が何を返すか、`title` 属性が何を含むか）。

前回見つけた抜け道（確認さえすれば満たせてしまう基準）は塞がった。
1行足しただけのルールだが、**基準を書くときに動詞で引っかかる**のが効いている。

## 仕様が実装中に変わった箇所

なし。仕様に書いた通りに実装が通った。3回の振り返りで初めてである。

ただしこれを「仕様の質が上がった」と読むのは早い。0009は
**触る関数が1つ（`insertSnippet`）と決まっていて、既にテストがあった**。
0014でテストを入れ、0009の起票時に前提の誤りを潰してあったので、
仕様を書く時点で分からないことがほとんど残っていなかった。
条件が楽だっただけ、と見るのが妥当。

## `## 未確認の前提` が別の用途に使われた

0009でこの節に挙げた2つは、どちらも**確かめるつもりのない前提**だった。

- `execCommand('insertText')` なら履歴を保てるはずだが、採らない
- `aria-label` の読み上げは実地確認しない

これは本来の用途と違う。この節は1回目の振り返りで「**実装の最初にそこから
確かめる**ための場所」として入れたものであって、「確かめないと宣言する場所」
ではない。今回は実質「スコープ外の宣言」として使っていた。

害があったかというと、なかった。むしろ「なぜ確かめないか」が仕様に残ったのは
よかった。ただし節の名前と用途がずれたまま増えると、**実装の冒頭に確かめる
リスト**としての機能が薄まる。確かめるものと確かめないものが同じ箱に入っていると、
どれを先に潰すべきか分からなくなる。

→ 様子を見る。今回1件だけなので、ルールを足すほどではない。
次回また同じ使われ方をしたら、節を分ける（`## 未確認の前提` と
`## 確かめないと決めたこと`）ことを提案する。

## 受け入れ基準で捕まえられなかった問題

**検証チェックどうしが汚染し合っていた。**

0009の実機検証を足して43/43件OKになったが、出力をよく見ると、
「囲める記号は選択したテキストを包む」のチェックが
`\sqrt{# 二次方程}\alpha 式の解の` を見ていた。前のチェックで挿入した
`\alpha` が自動保存で復元され、その文書に対して次のチェックを流していた。

**チェックは通っていた**（包む挙動は確かに起きている）。しかし意図した条件では
なかった。基準の書き方の問題ではなく、**検証スクリプトが状態を持つ**ことの問題で、
0001で自動保存を入れた時点から潜在していたものが、初めて表に出た。

直した（保存の落ち着きを待ってからlocalStorageを消して開き直す）が、
気づいたのは `OK` の行に出した実際の値を読んだからで、件数だけ見ていたら
通り抜けていた。CLAUDE.mdに「スクリーンショットを実際に見る」はあるが、
**チェックが見ている値を読む**とは書いていない。

→ これは [0017](../issues/0017-verify-script-structure.md)（検証スクリプトの
区分け）に直結する。区分ごとに流せるようにするなら、**各区分は既知の初期状態から
始める**が要件になる。0017のメモに追記した。CLAUDE.mdは変えない。
