## 前回の変更は効いたか

### 「画面に要素を足すissueは、その要素が占める幅・高さを測って書く」— 効いた。が、測る対象を取り違えた

0011の仕様では、検索欄を置く前にパレットの高さを3つの幅で実測した
（1280px = 94px / 720px = 94px / 600px = 126px、タブ行の残り幅も測った）。
そのおかげで「タブ行に同居させれば広い画面と狭い画面では0px、720px付近でだけ
+32px」と**書いてから実装でき**、置き場所の判断が1往復で済んだ。
実装後の実測は94 / 124 / 126pxで、見込みどおりだった。

**それでも幅600pxで事故った。** 検索結果が40件当たると、パレットが画面の
**65%（523px）**を占め、ソースが82px（2行）しか残らなかった。

測ったのは「足した要素そのもの（検索欄 180×28px）」で、測らなかったのは
**その要素が開く領域（検索結果の欄）**である。ルールの文が「その要素が占める
幅・高さ」なので、**可変の大きさで開く領域**が視界から漏れた。
検索欄は28pxだが、検索欄が開く結果の欄は最大523pxだった。

→ **提案1**: ルールに「その要素が開く領域が最大でどれだけ占めるかも測る」を足す。

## 仕様が実装中に変わった箇所

0011では4件変わった。うち2件は**同じ原因**である。

### 1. 上限40件（前提が崩れた）— 測れる道具を持っていたのに、片方しか測らなかった

上に書いたとおり。悪いのは見落としそのものより、**同じ道具で測れたのに測らなかった**
ことである。パレットの高さはヘッドレスChromiumで測ったのに、
「40件出たときの高さ」は測らず `## 未確認の前提` に送った。
仕様の時点で2分で測れたものを、実装を終えてから測り、仕様へ戻る往復になった。

`## 未確認の前提` は「**いま確かめる手段がないもの**」を書く欄であって、
「確かめられるが面倒なもの」の置き場ではない。3回目の振り返りで
「別の用途に使われた」と書いたのと、形を変えた同じ問題だと思う。

### 2. 受け入れ基準に書いた固有名が実データに無かった（`taylor`）

「`taylor` と `テイラー` で公式が引ける」と書いたが、公式60件にテイラー展開は
無かった。テストを書いて初めて落ちた。`parts` / `部分積分` に直した。

### 3. 「挿入すると `.katex` が1つ増える」が実態と合わなかった

既存の `$x$` の中に挿入するので数式の数は増えない（1 → 1 で落ちた）。
0029と同じく「∫として描画される」に直した。こちらのほうが強い基準でもある。

**2と3はどちらも、実データや実画面を見ずに受け入れ基準を書いたために起きた。**
CLAUDE.mdは「**背景**に現状を書くときは、推測で書かず実際にファイルや画面を見てから
書く」と言っている（3回目の振り返りで足した行）。今回推測で書いたのは背景ではなく
**受け入れ基準**だった。基準は「上から確認する一覧」なので、ここが実データと
ずれていると、検証の時点で必ず往復になる。

→ **提案2**: その行の「背景」を「背景と受け入れ基準」に広げる。

### 4. 検索欄を `role="tablist"` の子から外した

`.palette__tabs`（`role="tablist"`）の子に入力欄を置くのはARIA的に正しくない。
`.palette__bar` を作り、タブは `display: contents` で同じ行に並べた。
実装の細部で、ルールにする話ではない。記録にとどめる。
