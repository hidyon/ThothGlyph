## 引っかかり: 5件たまるまで切り出さなかった

CLAUDE.mdは「2〜3件クローズしたとき、自分から切り出す」と書いているのに、
0035・0021・0037・0040・0043と5件続けた。数えそこねた理由ははっきりしていて、
**クローズの手順（4文書の更新・token-usage.mdへの追記・マージ）には振り返りの
件数を数える場所がない**。前回の振り返りの対象から何件目かは、
`docs/retrospectives/` の最新ファイルを開かないと分からない。

ただし新しいルールを足す前に、今回は**ユーザーが「続きをしよう」と言った時点で
自分から数えて切り出せている**。仕組みではなく、セッションの開始時に
issue一覧と retrospectives を一緒に読む習慣で足りていた。ルールは足さない。

## 前回（8回目）の変更は効いたか

### 提案1「いちばん大きくなる状態で測る」— 効いたが、抜けが1種類あった

0037は幅360px（いちばん狭い画面）で図の寸法を測り、0043はバーを開いた状態
（いちばん高くなる状態）で41→42px・73→75pxまで測った。前回のルールどおり。

抜けたのは**画面の大きさの組**のほうだった。0043の受け入れ基準に
「幅360pxでtextareaが207px以上」と書いたが、この207pxは0012・0032から
引き継いだ**幅375px・高さ667px**の数字で、幅360pxは高さ640pxで測っている。
実測は194pxで、基準のほうが誤っていた（画面が低いぶん当然低い）。

前回のルールは「状態」（保存状態・文言・言語）を挙げていて、
**測った画面の大きさそのもの**は挙げていない。数値を前のissueから引き継ぐときに、
その数値がどの条件で測られたかが一緒に運ばれていない。

→ **提案1**: 仕様に寸法の数値を書くときは、測った条件（幅×高さ・言語・状態）を
数値の隣に書く。

### 提案2「規則を書いたら例を3件並べる」— 効いた

0043の「検索の規則」は、検索語・置換語・結果の表を6件持っている
（`sqrt` / `SQRT` / `\int` / 空文字 / `x + 1` など）。0037も「式の文法」に
受け付ける式と受け付けない式を並べた。**どちらも仕様どおりに実装され、
規則の食い違いは出ていない**。0034で起きた「仕様の内側での食い違い」は再発しなかった。

### 提案3「検証の前に `npm run build` を通す」— 効いた

「構文の壊れが『要素が出ない』という遠い症状で出る」は再発していない。

## 仕様が実装中に変わった箇所

### 0043: 「選択される」という基準は、見えることを担保していなかった（いちばん大きい）

仕様は一致の見せ方を「textarea上で選択される」と書いていた。実装して動かすと
動作としては正しいのに、**利用者からは「ヒットした箇所が識別しづらい」**と
指摘が来た。実測すると**フォーカスの無いtextareaの選択をChromiumが一切
描画していない**（`::selection` で色を指定しても描かれない）。

基準を「塗られて見て分かる」に書き直し、textareaの裏に同じ書式の層を敷いて
一致だけを塗る形に作り直した。ここで層の重なり順・末尾の改行・
縦スクロールバーのぶんの幅と、性能（400件で60ms/文字 → 38.9ms/文字）まで
3つ踏んでいる。**issue1件のなかでいちばん大きい変更が、受け入れ基準の
書き方から生まれた**。

CLAUDE.mdには既に「受け入れ基準は外から観測できる結果で書く」がある。
「選択される」はその意味では外から観測できる（`selectionStart` が読める）。
足りなかったのは、**利用者が見て分かるかどうか**という一段だけ厳しい条件で、
0043はまさにそこで落ちた。

→ **提案2**: 見た目が論点の基準は「スクリーンショットで見て分かる」で書く。

### 0037: 図の左余白が足りず、目盛りの文字が切れた

幅360pxで目盛りの文字を18ユーザー単位に上げたところ、`-4.24` が図の左端から
はみ出した。**スクリーンショットの目視で見つけた**（左余白を36→60に広げ、
「目盛りの文字が図の左端からはみ出さない」を検証に足した）。

8回目の0034（ボタンの並びが散らばった）と同じ形で、
**寸法の数値の基準だけでは拾えず、スクショを見て見つかった**2例目になる。
ルールは既にある（検証フェーズの「UIの変更はスクリーンショットを見る」）ので
足さない。守られていて、実際に2回とも拾っている。

### 0037: 基準にした初期チャンクの数値が古かった

仕様は「初期チャンク243.20 kBを増やさない」と書いていたが、それは0024の
実装直後の値で、現在のmainは既に247.13 kBあった。測り直して +0.80 kB という
差の形に書き換えた。提案1と同じ線で、**引き継いだ数値がいつのものか**である。

### 0040: 未確認の前提が崩れたが、往復にはならなかった

「サンプル文書が長くなると幅360pxの初期表示でグラフが画面外に出るかもしれない」を
未確認の前提に挙げていて、**実際に画面外だった**。ただし仕様の時点で
「撮って確かめる」と書いてあったため、撮って確かめてそう記録しただけで終わった。
**崩れることを想定して書いた前提は、崩れても往復にならない**。

## 受け入れ基準で捕まえられなかった問題

### 0021: 素のtextareaで測った前提が、実アプリで崩れた

`execCommand` を採る判断は素のtextareaで4本のプローブを流して固めたが、
打鍵のUndoの粒度が実アプリ（React＋重い再描画）では1文字ずつになり、
「3回打って3段戻る」という基準が検証で落ちた。
**アプリの上で測れる前提は、アプリの上で測る。**

### 0021: 既存の不具合（0036）を踏んで検証が5秒詰まった

保存状態の表示で待つヘルパが詰まり、`beforeunload` で古い文書が書き戻された。
0021とは無関係の既存不具合だが、**「表示で待つ」より「保存されたデータで待つ」
ほうが壊れにくい**という形で検証の書き方に返ってくる。
[0036](../issues/0036-save-status-stuck.md) は未着手のまま残っている。
