# issueごとの所要トークン

issueを1件片付けるのにどれだけのトークンを使ったかの記録。見積りの材料にする。

## 数え方

Claude Codeのセッションログ（`~/.claude/projects/<プロジェクト>/<セッションID>.jsonl`）の
各アシスタントメッセージの `usage` を合計する。

```bash
python3 - <<'PY'
import json, sys
tot = {}
for line in open(sys.argv[1] if len(sys.argv) > 1 else 0):
    try: d = json.loads(line)
    except ValueError: continue
    u = (d.get('message') or {}).get('usage')
    if not u: continue
    for k, v in u.items():
        if isinstance(v, int): tot[k] = tot.get(k, 0) + v
print(tot, '合計', sum(tot.values()))
PY
```

注意:
- `cache_read` が大半を占める。同じ文脈を読み直すたびに積み上がるので、
  「会話の長さ×やり取りの回数」に効く数字であって、成果物の量とは比例しない。
- セッションを跨いでissueを進めた場合は、該当する全セッションのログを足す。
- 下の数値はissueをクローズした時点のもの。コミットやこの表の更新自体は含まない。

0014・0006・0007は1つのセッションで連続して進めたため、内訳（出力／キャッシュ）は
分けられない。合計は、各issueをクローズしたコミットの時刻で区切った累積の差。
**0014の611万には、issueを10件起票した作業と、3本の仕様を書いた分が含まれる**ので、
テスト土台そのもののコストはこれより大幅に小さい。

所感（0001）: 仕様を書く→実装→実機検証の3往復で、検証スクリプトの失敗と
修正が2回。1回のやり取りごとに会話全体を読み直すため、キャッシュ読みが95%を占める。

所感（0014・0006・0007）: 会話が長くなるほど1回のやり取りが高くつく。同じ3件でも、
セッションを分けて短い文脈で進めれば総額は下がったはず。逆に、仕様を3本まとめて
書いて承認を1回にまとめたことは、やり取りの回数を減らす方向に効いている。

所感（0016・0002）: 0002の875万が突出している。原因は issue のサイズではなく、
**同じセッションで7件目のissueだったこと**。会話が長いほど1往復あたりの
キャッシュ読みが増えるので、同じ作業でもセッションの後半ほど高くつく。
0006（約88万、セッション前半の小さな修正）と比べると10倍の開きがある。

対策として考えられるのは、issueごと、あるいは仕様→実装→検証の区切りで
セッションを分けること。ただし文脈を引き継ぐ手間と引き換えになる。

所感（0009）: 約26万。0002の875万の1/33で、これまでで最も安い。
issueの規模が小さいこともあるが、効いたのは**新しいセッションの1件目だったこと**。
0016・0002で立てた「セッションを分けると下がる」という仮説を裏づける数字になった。
仕様→実装→検証を1往復ずつで通せた（実機検証の修正2回のみ）ことも大きい。

所感（0026）: 約12万でこれまでで最も安い。issueの中身が設定2行で、
起票の時点で `tsc --strict` を実測してエラー0件と分かっていたため、
仕様にも実装にも迷いが入らなかった。**起票時に測っておくと、仕様と実装の
両方が短くなる**という形で効いている。
ただし同じセッションで0009→issue起票6件→0026と進めており、セッションの
後半ほど高くなるという傾向自体は変わっていない（0009の26万より安いのは
作業量の差による）。

所感（0031）: 約11万で、翻訳約182件・新規5ファイル・検証18件を足した割に安い。
効いたのは**仕様が前のセッションで書き上がっていた**ことで、このセッションは
「2状態への修正 → 承認 → 実装 → 検証」を一直線に進めた。仕様の分の消費は
別セッションに乗っている（表の注意書きどおり本来は足すべきだが、前セッションの
ログを持っていないので、この数字は実装以降だけと読むこと）。

翻訳の量そのものはほとんど効かなかった。182件を1件ずつ書くのではなく、
対応表を持ったスクリプトで一括変換したため。**同じ形の編集がN件あるときは、
N回の編集ではなく1回の変換として書く**と、量が消費に乗らない。

所感（0019）: 約28万。0031（11万）の2.5倍で、同じセッションの2件目としては高い。
上がった理由ははっきりしていて、**仕様の前提が実装で崩れた**こと。被覆率の
測り方を変え、太さを9通り振って測り直し、仕様の数字を入れ替える往復が入った。
5回目の振り返りで「未確認の前提を実測した」0018が安かったのと対照的で、
**起票や仕様の時点で測れるものは測っておくほうが安い**という同じ線の上にある。
今回は「アイコンがまだ無いので仕様段階では測れない」という事情があり、
その分が実装に回った。

`/design` でキャンバスを作ったぶんも乗っている。ただし4案を絵にして比べたことで
題材の判断が1往復で済み、コントラスト比の誤りもそこで見つかった。
