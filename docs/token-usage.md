# issueごとの所要トークン

issueを1件片付けるのにどれだけのトークンを使ったかの記録。見積りの材料にする。

## 数え方

Claude Codeのセッションログ（`~/.claude/projects/<プロジェクト>/<セッションID>.jsonl`）の
各アシスタントメッセージの `usage` を合計する。

```bash
python3 - <<'PY'
import json, sys
tot = {}
for line in open(sys.argv[1] if len(sys.argv) > 1 else 0):
    try: d = json.loads(line)
    except ValueError: continue
    u = (d.get('message') or {}).get('usage')
    if not u: continue
    for k, v in u.items():
        if isinstance(v, int): tot[k] = tot.get(k, 0) + v
print(tot, '合計', sum(tot.values()))
PY
```

注意:
- `cache_read` が大半を占める。同じ文脈を読み直すたびに積み上がるので、
  「会話の長さ×やり取りの回数」に効く数字であって、成果物の量とは比例しない。
- セッションを跨いでissueを進めた場合は、該当する全セッションのログを足す。
- 下の数値はissueをクローズした時点のもの。コミットやこの表の更新自体は含まない。

0037はこれまでで最も大きい（これまでの最大0035の約1.7倍）。機能の検討・issueの
起票・仕様の実測・新規ファイル3つの実装・検証までを1セッションで通したため。
新しい記法と評価器を作るissueは**この規模になる**と見ておく。

0014・0006・0007は1つのセッションで連続して進めたため、内訳（出力／キャッシュ）は
分けられない。合計は、各issueをクローズしたコミットの時刻で区切った累積の差。
**0014の611万には、issueを10件起票した作業と、3本の仕様を書いた分が含まれる**ので、
テスト土台そのもののコストはこれより大幅に小さい。

所感（0001）: 仕様を書く→実装→実機検証の3往復で、検証スクリプトの失敗と
修正が2回。1回のやり取りごとに会話全体を読み直すため、キャッシュ読みが95%を占める。

所感（0014・0006・0007）: 会話が長くなるほど1回のやり取りが高くつく。同じ3件でも、
セッションを分けて短い文脈で進めれば総額は下がったはず。逆に、仕様を3本まとめて
書いて承認を1回にまとめたことは、やり取りの回数を減らす方向に効いている。

所感（0016・0002）: 0002の875万が突出している。原因は issue のサイズではなく、
**同じセッションで7件目のissueだったこと**。会話が長いほど1往復あたりの
キャッシュ読みが増えるので、同じ作業でもセッションの後半ほど高くつく。
0006（約88万、セッション前半の小さな修正）と比べると10倍の開きがある。

対策として考えられるのは、issueごと、あるいは仕様→実装→検証の区切りで
セッションを分けること。ただし文脈を引き継ぐ手間と引き換えになる。

所感（0009）: 約26万。0002の875万の1/33で、これまでで最も安い。
issueの規模が小さいこともあるが、効いたのは**新しいセッションの1件目だったこと**。
0016・0002で立てた「セッションを分けると下がる」という仮説を裏づける数字になった。
仕様→実装→検証を1往復ずつで通せた（実機検証の修正2回のみ）ことも大きい。

所感（0026）: 約12万でこれまでで最も安い。issueの中身が設定2行で、
起票の時点で `tsc --strict` を実測してエラー0件と分かっていたため、
仕様にも実装にも迷いが入らなかった。**起票時に測っておくと、仕様と実装の
両方が短くなる**という形で効いている。
ただし同じセッションで0009→issue起票6件→0026と進めており、セッションの
後半ほど高くなるという傾向自体は変わっていない（0009の26万より安いのは
作業量の差による）。

所感（0031）: 約11万で、翻訳約182件・新規5ファイル・検証18件を足した割に安い。
効いたのは**仕様が前のセッションで書き上がっていた**ことで、このセッションは
「2状態への修正 → 承認 → 実装 → 検証」を一直線に進めた。仕様の分の消費は
別セッションに乗っている（表の注意書きどおり本来は足すべきだが、前セッションの
ログを持っていないので、この数字は実装以降だけと読むこと）。

翻訳の量そのものはほとんど効かなかった。182件を1件ずつ書くのではなく、
対応表を持ったスクリプトで一括変換したため。**同じ形の編集がN件あるときは、
N回の編集ではなく1回の変換として書く**と、量が消費に乗らない。

所感（0019）: 約28万。0031（11万）の2.5倍で、同じセッションの2件目としては高い。
上がった理由ははっきりしていて、**仕様の前提が実装で崩れた**こと。被覆率の
測り方を変え、太さを9通り振って測り直し、仕様の数字を入れ替える往復が入った。
5回目の振り返りで「未確認の前提を実測した」0018が安かったのと対照的で、
**起票や仕様の時点で測れるものは測っておくほうが安い**という同じ線の上にある。
今回は「アイコンがまだ無いので仕様段階では測れない」という事情があり、
その分が実装に回った。

`/design` でキャンバスを作ったぶんも乗っている。ただし4案を絵にして比べたことで
題材の判断が1往復で済み、コントラスト比の誤りもそこで見つかった。

所感（0011）: 約1343万で、これまでで最も大きい。内訳の大半（94%）は
`cache_read` で、**1セッションで0010の仕様を書き上げてから0011へ乗り換えた**ぶんが
そのまま乗っている。乗り換えの時点で文脈は捨てられないので、
**着手するissueを決めてからセッションを始めるほうが安い**。

もう1つは実機測定の往復。仕様の時点でパレットの高さを測った（94/94/126px）のは
効いていて、置き場所の判断が1往復で済んだ。一方で「上限40件が多すぎないか」は
測らずに未確認の前提へ送り、実装後に崩れて仕様へ戻る往復になった。
**同じ道具（ヘッドレスChromium）でその場で測れるものは、仕様の時点で測っておく**
という線は0019・0018と同じ。

所感（0024）: 約1076万。0011（1343万）に次いで大きいが、**乗り換えは一度もなく、
issueを選ぶところから検証まで一直線に進んだ**セッションでこの額になっている。
効いたのは往復の回数ではなく**1往復あたりの重さ**で、ビルド・測定・全区分の検証を
そのつど流すため、1回のやり取りごとに長い出力が文脈へ積み上がる。

仕様の時点で実測したもの（依存ごとの内訳、2条件の読み込み時間）は、そのまま
受け入れ基準の数値になって実装後の判断が1回で済んだ。一方、**測らずに未確認の前提へ
送った「ソース表示にしたときのパレットの高さ」は実装後に崩れ**、幅を詰める修正と
再検証の往復になった。0019・0011と同じ線で、**その場で測れるものは仕様の時点で測る**。

安くできた余地としては、検証の全区分（38.7秒・125件）を実装の途中で何度も流した
ぶんがある。区分を選んで流せる仕組み（0017）があるのだから、
**途中は `loading` だけ、最後に全区分**と決めておくほうが軽い。

所感（0032）: 約930万。0024（1076万）と同じセッションの2件目で、**CSSだけで閉じた
issueとしては高い**。中身を見ると出力6.6万に対してキャッシュ読みが915万で、
**同じセッションで2件目をやること自体の値段**がほとんどを占めている
（1件目の文脈を全部読み直しながら進むため）。0011の所感で書いた
「着手するissueを決めてからセッションを始めるほうが安い」の裏返しで、
**1セッション1issueで切るほうが安い**という同じ線。

仕様の前に全タブ・全分類の高さを実測した（8タブ×2画面＋12分類）のは効いていて、
「タブが高さの2/3を使っている」が分かったので設計が1案で決まった。
一方で**受け入れ基準の1つ（高さの差20px以内）は測る前に書いた数字**で、
実装後に外れた（短いほうへ外れたので悪化ではない）。基準に数値を書くなら、
その数値も実測から出す。

所感（0033）: 約713万。**1セッションの1件目**で、issueを選ぶところから
マージまで一直線に進んだ。0032（930万、同じセッションの2件目）より安く、
「1セッション1issueで切るほうが安い」の線に乗っている。

効いたのは、**起票の時点で幅ごとの実測表があった**こと（0033のissueは0032の
検証中に測った数値を持って起票されていた）。仕様を書く前の測定は
「溢れ始める幅（日本語435px・英語446px）」と「短縮ラベルでの幅」の2回で済み、
境目を480pxに決める判断が1往復で終わった。

高くついたのは検証の往復で、全区分（46秒・150件）を2回流している。
1回目は自分で足したチェックが揺れて落ちた（結果表示が消える前に読めていなかった）。
**新しく足すチェックが時間に依存するなら、最初から待ちを入れて書く**ほうが安い。

所感（0012）: 約1098万（セッション累計1811万から0033のぶんを引いた差）。
**同じセッションの2件目**で、1件目（0033、713万）の1.5倍。0024→0032、
0009→0026と同じ並びで、**セッションの後半ほど1往復が高い**という傾向はここでも出た。

中身としては、これまでで最も広いissue（新しい純粋関数＋単体テスト14件＋
コンポーネント2つ＋CSS＋検証32件＋4文書）でありながら、**仕様に戻る往復は
なかった**。効いたのは仕様の前に置き場所を測ったことで、
「ツールバーには入らない／見出し行なら入るが、そのままだと30px→36pxに伸びて
textareaが207px→201pxに減る」まで数字で出してから書いたので、
実装は測った値をCSSに写すだけで済んだ。

未確認の前提3つ（隠したinputへのsetInputFiles、DataTransferでのドロップ、
File.text()）は**すべて成立**した。0011・0024・0019では未確認の前提が崩れて
往復になっていたので、対照的な結果になっている。3つとも
「実装の最初に1回試せば分かる」種類だったのが違いで、**仕様の時点で測れないものは、
実装の最初に確かめる順番を仕様に書いておく**と往復が1回に収まる。

高くついたのは検証で、区分 `file-load`（49秒・32件）と全区分（96秒・182件）を
流している。0024の所感で書いた「途中は1区分だけ、最後に全区分」は守れた。
一方で、書き間違い（属性の閉じ忘れ）で開発サーバが500を返し、検証が
タイムアウトして原因を追う往復が1回入った。**まとめて書き換えたあとは、
検証の前にビルドか型チェックを通す**ほうが安い（今回はtscが通ってしまったので、
`curl` で開発サーバの応答を見るまで分からなかった）。

所感（0034）: 約637万。**同じセッションの3件目なのに2件目（0012、1098万）より安い**。
これまでの「セッションの後半ほど高い」に対する初めての逆転で、理由は
0012の土台（見出し行という置き場所、結果表示の枠、検証の書き方、
純粋関数の切り分け方）を**そのまま流用できた**こと。設計の判断がほとんど要らず、
仕様も実装も0012の形をなぞるだけで済んだ。

**1セッション1issueは、隣接しないissueを並べたときの話**だと分かった。
同じ画面・同じ仕組みの続き（0017+0027、0032+0033、0012+0034）は、
続けてやるほうが安い。着手順を決めるときは、
**次のissueが前のissueの土台に乗るかどうか**を見るとよい。

所感（0035）: 約1673万。**コードの振る舞いを1行も変えていないissueとしては突出**して
いる（同じセッションの4件目で、振り返り1本を挟んだ後という位置も効いている）。
内訳は例によってキャッシュ読みが99%で、**セッションの長さがそのまま値段**になった。

中身の面では、**仕様の途中でスコープが変わった**のが効いている。
「スクリーンショットは載せない」で承認を取りにいったところ、
「アイコンとスクショを入れて、開発者向けはほぼ不要」と返ってきて、
仕様を書き直して承認を取り直した。**見せ方の好みは、仕様を書く前に聞くほうが安い**
（測れば決まる寸法と違い、こちらの実測では決まらない）。

安く済んだ部分もある。READMEに書く件数（記号88個・公式60件・12分類）は
**実データを数えてから書き**、さらに単体テストで固定したので、
「数が合っているか」を人手で確かめる往復が消えた。
書いた具体例（`x + 1` を選んで `√` → `\sqrt{x + 1}`、検索語 `積分` / `\int`）も
`insertSnippet` と `searchPalette` を実際に呼んで確かめた。
**文章のissueでも、数字と例は実行して確かめられる**。

所感（0021）: 約962万。**実装の前に実測を挟んだぶんが安く効いた**issue。
`execCommand` を採るかどうかが判断の中心だったので、仕様を書く前に
素のtextareaで4本のプローブを流し、`setRangeText` が履歴に乗らないことと、
**挿入の前後に `setSelectionRange` を挟まないとUndo単位がまとまってしまう**ことを
数字で押さえた。おかげで実装は1往復で通り、仕様の承認も1回で済んでいる。

ただし**そのプローブを素のtextareaでしかやらなかった**ぶんは払った。
打鍵のUndoの粒度が実アプリ（React＋重い再描画）では1文字ずつになり、
受け入れ基準の「3回で3段」が外れて検証で落ちた。
**アプリの上で測れる前提は、アプリの上で測る**ほうが安い。

検証の後半2件が落ちたのは、0021とは無関係の既存の不具合（0036）を踏んだため。
保存状態の表示で待つヘルパが5秒詰まり、`beforeunload` で古い文書が書き戻されていた。
**「表示で待つ」より「保存されたデータで待つ」ほうが壊れにくい**。
