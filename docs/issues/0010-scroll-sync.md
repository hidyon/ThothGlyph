# 0010: ソースとプレビューのスクロールが連動しない

- 状態: closed
- 起票日: 2026-09-19

## 背景

左右のペインのスクロールが独立している。長い文書では、編集している段落が
プレビューのどこにあるのかを目で探すことになる。逆に、プレビューを読み返していて
直したい箇所を見つけても、ソースのどこかを探し直すことになる。

## やりたいこと

- エディタをスクロールすると、プレビューの対応する位置が一緒に動く。
- **プレビューをスクロールすると、エディタの対応する位置も動く**（双方向。
  2026-09-20に追加）。

## やらないこと

- **リロード後の位置とカーソルの復元**。もとは本issueに同梱していたが、
  2026-09-21に [0058](0058-restore-position.md) へ切り出した。0058は本issueで
  入る行とy座標の対応づけの上に乗るので、本issueが先。
- プレビュー側からエディタのカーソルを動かすこと。逆方向の同期で動かすのは
  スクロール位置だけで、カーソルと選択には触れない（読み返している最中に
  編集位置を失わないため）。
- プレビューのクリックでソースの該当箇所へ飛ぶこと
  （[0020](0020-preview-click-to-edit.md)）。

## メモ

- 行と出力の対応づけが要る。割合（スクロール量の比）で合わせる簡易版と、
  markedのトークンに行番号を持たせて要素へ埋める方式がある。
  **割合で合わせた場合のずれは実測した**（幅1440px）: 数式が満遍なく散る文書で
  38〜63px、前半が数式・後半が散文と偏った文書で165〜426px（約15行）。
  仕様では行番号の方式を採る。
- 双方向には**同期のループを止める仕組み**（動かされた側が動かし返さない）が要る。
- 仕様は [docs/specs/0010-scroll-sync.md](../specs/0010-scroll-sync.md)。
  2026-09-21に片方向の下書きから双方向・同期のみへ書き直し、同日クローズ。
  実測のずれは全点0px（基準32px以内）。入力コストが約6ms増えたぶんは
  [0059](0059-perf-headroom.md) へ起票した。
