# 0014: 単体テストの土台を入れる

- 状態: closed
- 起票日: 2026-09-19

## 背景

`lib/` は設計上の約束として純粋関数に寄せてあるのに、回帰を守るものがない。
いま検証手段は `scripts/verify-ui.mjs`（実機のUI操作）だけで、これは
「このLaTeXがこう変換される」ような細かい入出力を網羅するには重すぎる。

とくに `renderMarkdown.ts` の数式抽出は入り組んだ正規表現で、
[0006](0006-math-in-code.md) でここに手を入れる予定がある。いま壊れていない
ケース（通貨表記、`\$` のエスケープ、`$$` と `$` の優先、改行を跨ぐ式）を
固定しておかないと、直したつもりで別のものを壊す。

[0001](0001-autosave.md) の仕様では「テスト基盤がないので置かない」と決めた。
その判断の引き取り先がこのissue。

## やりたいこと

- `lib/` の関数に対する単体テストが書ける状態になり、コマンド1つで走る。
- 既存の `insertSnippet` / `renderMarkdown` / `documentStorage` に、
  現在の振る舞いを固定するテストがある。
- CLAUDE.mdの「検証」の節に、テストと実機検証の使い分けが書かれている。

## やらないこと

- カバレッジの目標値を決めること。
- コンポーネントのテスト（React Testing Library）。まず `lib/` に閉じる。
- CI（GitHub Actions）の設定。別issueにする。

## メモ

- Vitestが素直（Viteの設定を共有できる）。依存を足すので、CLAUDE.mdの
  「状態管理もUIフレームワークも入れない」方針との整合をユーザーと確認すること。
- `documentStorage` は `window.localStorage` に触るので、環境（jsdom）か
  スタブが要る。ここも仕様で決める。

## 結果（2026-09-19 クローズ）

Vitestを入れ、`lib/` の4ファイルに27件のテストを書いた（25件が通過、2件は
0006の不具合を記録する `it.fails()`）。仕様 [0014](../specs/0014-unit-tests.md) から
変えた点は、`renderMarkdown` のテストにjsdomが必要だったこと（DOMPurifyが
`window` を要求する）。仕様側にも追記した。

テストを1つ意図的に壊して `npm test` が失敗することも確認した。

副産物: `insertSnippet` は既に選択範囲を `%CURSOR%` の位置に包む実装だった。
[0009](0009-wrap-selection.md) の前提が誤っていたので、issueを書き直した。
