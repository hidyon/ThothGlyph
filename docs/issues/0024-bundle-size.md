# 0024: 初期バンドルが563kBある

- 状態: closed
- 起票日: 2026-09-19

## 背景

`npm run build` は毎回チャンクサイズの警告を出す。起票時点の実測:

| 成果物 | サイズ | gzip |
|---|---|---|
| `dist/assets/index-*.js` | **563.54 kB** | **174.77 kB** |
| `dist/assets/index-*.css` | 34.92 kB | 9.49 kB |

KaTeX・marked・DOMPurifyが全部この1つのJSに入っている。加えてKaTeXの
Webフォントが多数（`KaTeX_*.woff2` / `.woff` / `.ttf`）出力される。

このアプリは「開いてすぐ書き始める」道具なので、初回の読み込みが重いのは
使い始めの体験を直接損なう。回線の細い環境ではとくに効く。

## やりたいこと

- 初期バンドルが小さくなる（目標値は仕様で決める。現状563.54kBが基準）。
- 初回表示から入力できるようになるまでの時間が、いまより悪化しない。
- 分割したことで新しい待ち時間（プレビューが出るまでの空白など）が
  目に見えて増えない。

## やらないこと

- 依存ライブラリの置き換え。KaTeXもmarkedもDOMPurifyも
  [設計上の約束](../../CLAUDE.md)の一部であり、差し替えは別の話。
- Service Workerによるキャッシュ。[0019](0019-app-icon.md) のメモにあるPWA化と
  同じく、ここでは扱わない。

## メモ

- 分割の候補: KaTeXを動的importにする。ただしプレビューは初期表示で
  すぐ必要なので、遅延させると**初回描画が遅れる**。どちらを取るかが
  このissueの中心の判断になる。
- フォントのサブセット化で減らせる可能性があるが、どの記号が使われるかは
  利用者の入力次第なので、落とすと表示できない記号が出る。危険。
- 受け入れ基準には**ビルド出力のサイズ**（機械で読める）と、実機での
  初回描画までの時間（[0007](0007-preview-performance.md) と同じ測り方）の
  両方を数値で書くこと。
- `vite.config.ts` の `build.rolldownOptions.output.codeSplitting` で
  分割できるとViteの警告が示唆しているが、実際にどう効くかは**未確認**。

## 結果（2026-09-20）

[仕様](../specs/0024-bundle-size.md)のとおり、KaTeX・marked・DOMPurifyとKaTeXのCSSを
遅延チャンクへ出した。

| | 初期JS | 初期CSS | Fast 3G + CPU 4倍でtextareaまで | 同 数式まで |
|---|---|---|---|---|
| 分割前 | 579.98 kB（gzip 180.50） | 36.09 kB | 1964 ms | 2021 ms |
| 分割後 | 243.20 kB（gzip 76.82） | 6.32 kB | 1085 ms | 1939 ms |

バイト数の合計は変わらないが、**書き始められるまでが879 ms縮み、プレビューが出るまでは
悪化しなかった**（遅延チャンクの取得をReactのマウント前に始めているため）。
チャンクサイズの警告も出なくなった。
