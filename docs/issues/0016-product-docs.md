# 0016: プロダクト全体の仕様文書を書く

- 状態: closed
- 起票日: 2026-09-19

## 背景

`docs/specs/` にあるのはissue単位の仕様で、どれも「この変更で何が変わるか」しか
書いていない。プロダクト全体として**何を満たすべきか**（要求）、**どう組み立てて
いるか**（アーキテクチャ）、**いま何ができるか**（機能）、**どう確かめるか**
（テスト）が、どこにもまとまっていない。

いまは規模が小さいのでコードを読めば分かるが、issueが15件まで増えた段階で、
「この判断は既存のどの前提と矛盾するか」を確かめる相手がコードしかないのは重い。
仕様駆動開発の土台として、issue仕様の上位にあたる文書が要る。

## やりたいこと

- 要求仕様・アーキテクチャ・機能仕様・テスト仕様の4文書が `docs/` にある。
- 各文書が**現在の実装を正として**書かれていて、読めばコードを読まなくても
  全体像が分かる。
- issue仕様（`docs/specs/`）との役割分担が明示され、どちらを更新すべきか迷わない。

## やらないこと

- 未実装の要求（openのissue）を要求仕様に盛り込むこと。文書と実装の差が
  追えなくなる。未実装は「今はない」とissue番号だけ添える。
- 文書の自動生成。手で書いて手で保つ。

## メモ

- 4文書が実装から乖離する（＝嘘になる）のが最大のリスク。更新の責任を
  CLAUDE.mdに1行書くところまでやる。

## 結果（2026-09-19 クローズ）

`docs/` に4文書を置いた。記述した事実（ファイル構成、保存キー、パレット62件の
内訳、テスト35件の内訳、実機検証23件、性能の実測値）はコードと検証結果に
突き合わせて確認した。パレットの説明は実際の項目と合っていなかったので直した。

CLAUDE.mdに、issueクローズ時に4文書を見直す1行と、構成図への追加を入れた。
