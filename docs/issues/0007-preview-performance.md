# 0007: 長い文書でプレビューが重い

- 状態: closed
- 起票日: 2026-09-19

## 背景

1打鍵ごとに文書全体を marked と KaTeX にかけ直している（`App.tsx` の
`useMemo(() => renderMarkdown(source), [source])`）。短い文書では気にならないが、
長くなると入力が追従しなくなる。

実測（400節・400数式、ヘッドレスChromium）: 5文字の入力に **6.0秒**。
1文字あたり約1.2秒で、実用にならない。

## やりたいこと

- 数百の数式を含む文書でも、入力がひっかからずに打てる。
- プレビューの更新が遅れることはあってよいが、入力そのものは常に即座に返る。

## やらないこと

- 仮想スクロール（表示領域の外を描かない）。まず更新の仕方で足りるか見る。
- Web Workerへの移動。効果と複雑さの釣り合いを見てから。

## メモ

- 案1: プレビュー更新のデバウンス（入力が止まってから描く）。実装は小さいが、
  止まるまで何も更新されないので体感が変わる。
- 案2: ブロック単位でキャッシュし、変わった段落だけ描き直す。効果は大きいが
  分割の単位を決める必要がある。
- 案3: KaTeXの結果を LaTeX 文字列をキーにキャッシュする。同じ式を打ち直す場面には
  効くが、初回入力には効かない。
- 受け入れ基準に「400節の文書で N 文字の入力が M ミリ秒以内」の形で数値を入れること。
  検証は `scripts/verify-ui.mjs` に測定を足せばよい（今回の実測もその方法で採った）。

## 結果（2026-09-19 クローズ）

KaTeX出力のキャッシュ（上限500件のFIFO）と `useDeferredValue` の2つで解決した。
400節・400数式の文書で、1文字あたりの入力反映が **約1200ms → 29.2ms**、
入力を止めてからプレビューが追いつくまで308ms。

メモに残していた「ブロック単位の差分描画」は不要だった。目標に届いたので、
複雑さを足さずに済ませている。

検証: `npm test` 35件、実機23/23 OK、コンソールエラーなし。
