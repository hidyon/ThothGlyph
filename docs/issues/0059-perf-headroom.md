# 0059: 400節の文書で「追いつくまで」が基準1.5秒に余裕がない

- 状態: open
- 起票日: 2026-09-21

## 背景

[0010](0010-scroll-sync.md)（スクロールの同期）の検証で、`perf` 区分の数値を
実装の前後で測り直したところ、1文字あたりの入力反映が約6ms増えていた。

| | 1文字あたりの入力反映 | 入力を止めてから追いつくまで |
|---|---|---|
| 0010の前 | 31.6〜34.1ms | 277〜993ms |
| 0010の後 | 35.8〜40.2ms | 282〜1497ms |

（幅1440px・400節400数式・`--repeat 5` の幅。基準は50ms以内と1.5秒以内）

どちらも基準は満たしているが、**追いつくまでの最悪値1497msは基準1.5秒の
3ms手前**で、1回でも負荷が乗れば落ちる。増えたぶんは0010で入れた
`data-line`（400節の文書で800要素ぶん）がサニタイズとDOMへの反映を
重くしているため。

また、`test-spec.md` にそれまで書かれていた「29.2ms/文字・300〜500ms」は
測った環境が違う古い値で、実際の基準線は約32ms・約1秒だった。

## やりたいこと

400節の文書で、入力を止めてから追いつくまでの**最悪値**を基準の1.5秒に対して
余裕のある値（たとえば1秒以内）に戻す。1文字あたりの入力反映も、
0010の前の水準（約32ms）に近づける。

## やらないこと

- `data-line` をやめること。スクロールの同期（0010）とプレビューからの編集
  （[0020](0020-preview-click-to-edit.md)）の土台なので、外せない。
- 基準そのものを緩めること。緩めれば数字は通るが、体感は戻らない。

## メモ

- 効きそうな方向:
  - **アンカーの数に上限を設ける。** 0010の仕様にも「アンカーは数十〜数百あれば
    足り、細かくするほどコストが増える」と書いたが、上限は入れていない。
    400節の文書では800件付いている。間引いても補間で埋まる。
  - [0024](0024-bundle-size.md) のスコープ外に残した「起動時にラベル122件を
    KaTeXで一気に描くCPUコスト」と、見ている場所が近い。
- 測り方は `node scripts/verify-ui.mjs --repeat 5 perf`。
  **前後で必ず測り直すこと**（環境が違うと前の数値は当てにならない）。
