# 0010: ソースとプレビューのスクロールを連動させる

- 対応issue: [0010](../issues/0010-scroll-sync.md)
- 状態: approved（2026-09-21にユーザーの承認を得た）
- 作成日: 2026-09-19（2026-09-21に双方向・同期のみへ書き直し）

> 2026-09-19の下書きは**片方向・位置の復元つき**で書かれていた。2026-09-21に
> 範囲を決め直し、**双方向・同期のみ**にした。位置とカーソルの復元は

## 目的

長い文書を書いているとき、いま編集している段落がプレビューのどこにあるのかを
探さずに済むようにする。また、プレビューを読み返していて直したい箇所を見つけたとき、
ソースのどこかを探さずに済むようにする。

エディタをスクロールするとプレビューが追い、プレビューをスクロールすると
エディタが追う。**追うのはスクロール位置だけ**で、カーソルと選択範囲には触れない。

## 仕様

### 1. 行の対応づけ — 割合ではなく行番号で合わせる

issueのメモにある2案のうち、**行番号で合わせる案を採る**。

割合（スクロール量の比）で合わせた場合のずれは実測した（幅1440px・日本語・
ライト、40節／ブロック数式13・表8・コードブロック5を含む文書。エディタの
スクロール範囲6856px、プレビュー7206px）:

| 上端に合わせた見出し | 割合での位置 | 正しい位置 | ずれ |
|---|---|---|---|
| 節10 | 1576px | 1621px | 45px |
| 節20 | 3427px | 3558px | 131px |
| 節30 | 5478px | 5660px | 181px |
| 節36 | 6829px | 7080px | 251px |

プレビューの行の高さは28pxなので、251pxは**約9行**ぶん。ずれは文書の後ろほど
大きくなる。このエディタでいちばんよく使う書き方（数式・表）がいちばんずれるので、
割合では目的を満たさない。

`renderMarkdown` の出力するトップレベルのブロック要素に、そのブロックが始まる
**元ソースの行番号**を `data-line="N"`（1始まり）として付ける。

```
# 見出し          →  <h1 data-line="1">見出し</h1>
                     （空行）
本文              →  <p data-line="3">本文</p>
```

- 付けるのはトップレベルのブロックだけ。入れ子（`li`、`td`）には付けない。
  アンカーは数十〜数百あれば足り、細かくするほど測定のコストが増える。
- 何も出力しないトークン（`space`）には付けない。開始タグで始まらない出力
  （HTMLコメントだけの行など）にも付けない。アンカーが1つ減るだけで、
  前後のアンカーからの補間で足りる。
- KaTeXの出力（差し戻される数式HTML）とグラフのSVGには付けない。差し戻しは
  サニタイズの後なので、`data-line` はサニタイズの前に入り、そのまま残る
  （DOMPurifyが落とさないことは実測済み）。

実装は `marked.lexer()` でトップレベルのトークンに分け、トークンごとに
`marked.parser([token])` して**先頭の開始タグに属性を差し込み**、連結する。

```
/^(\s*<[a-zA-Z][a-zA-Z0-9-]*)/ に ` data-line="N"` を差し込む
```

**行番号は数式とグラフを退避する前のソースで数える。** `$$...$$` は複数行を
1つのプレースホルダに畳むので、退避後のテキストで数えると以降が全部ずれる。
`extractBlocks` に**オフセットの対応表**を返させる。

```ts
/** 退避後のテキスト上の位置と、元ソース上の位置の対応。置換のたびに1件増える。 */
type OffsetMap = { masked: number; original: number }[]
```

トークンの `raw` を順に足すと退避後のオフセットが出る（`raw` の連結が
退避後のテキストと完全に一致することは実測済み）。それを対応表で元ソースの
オフセットへ直し、行頭オフセットの配列を二分探索して行番号にする。

### 2. エディタ側の行の位置を測る — ミラー要素

`<textarea>` は行の座標を返さないので、同じ書体・同じ幅・同じ折り返しの
**ミラー要素**を隣に置いて測る。0043で入った `.editor-highlights` と同じ手で、
**書式の指定も同じルールにまとめる**（`.editor, .editor-highlights, .editor-mirror`）。

- `.editor-mirror` は `.editor-wrap` の中に `position: absolute` / `inset: 0` /
  `visibility: hidden` / `overflow: hidden` / `pointer-events: none` /
  `aria-hidden` で置く。絶対配置なので**他の要素を1pxも押しのけない**
  （占める幅・高さは0px）。`visibility: hidden` なので描画もされない。
- 中身は**Reactでは描かず、計測のときに `innerHTML` で入れる**。
  31KBの文字列を打鍵のたびに描き直さないため（0043の塗る層は検索中だけ
  存在するが、ミラーは常時あるので同じ作りにはできない）。中身はUIではなく
  測定用の目盛りなので、Reactの管理下に置く利得がない。
- 文字列は `lib/mirrorHtml.ts` の純粋関数が作る。`&` `<` をエスケープし、
  アンカー行の先頭に `<span data-line="N"></span>` を置く。
  **末尾に改行を足す**（`pre-wrap` では末尾の改行が行にならず、1行ぶん縮む。0043）。
- アンカーの行番号は**プレビューのDOMから読む**（`[data-line]`）。同じ配列を
  両側で使うので、対応づけがずれない。
- 縦スクロールバーが出るとtextareaの折り返しが早くなるので、
  `.editor-highlights` と同じく**バーの幅だけミラーの `right` を詰める**
  （`textarea.offsetWidth - textarea.clientWidth`）。

空の `<span>` の `offsetTop` は行の上端より**3px下**に出る（行間の半分。
幅1440px・`line-height: 23.8px` で実測）。全アンカーに等しく乗る定数なので、
補正しない（基準の32pxに対して無視できる）。

### 3. アンカーの組と補間 — `lib/scrollMap.ts`

両側のアンカーを行番号で突き合わせ、**「エディタのy座標 → プレビューのy座標」の
対応表**にする。行番号は突き合わせの鍵としてだけ使い、補間そのものは
y座標どうしで行う。逆方向は同じ対応表を裏返すだけで済む。

```ts
type Anchor = { line: number; top: number }
type Pair = { from: number; to: number }

/** 行番号で突き合わせ、from の昇順に並べる。片方にしか無い行は捨てる。 */
export function pairAnchors(from: Anchor[], to: Anchor[]): Pair[]

/**
 * from 側の位置 value を to 側へ写す。
 * - 組を挟む位置は線形補間
 * - 最初の組より手前は 0 〜 最初の組の間で比例
 * - 最後の組より後ろは 最後の組 〜 末尾（fromEnd / toEnd）の間で比例
 * - 組が0件なら fromEnd / toEnd の比（＝割合での同期）に落ちる
 * 結果は 0 〜 toEnd に収める。
 */
export function mapScroll(pairs: Pair[], value: number, fromEnd: number, toEnd: number): number
```

`fromEnd` / `toEnd` は `scrollHeight - clientHeight`（スクロールできる最大量）。
末尾をこれで留めるので、**片方を最下端にすればもう片方も最下端になる**。

逆方向（プレビュー → エディタ）は `pairAnchors` の引数を入れ替えた組を使い、
同じ `mapScroll` を呼ぶ。**逆方向のための計算は1行も増えない。**

### 4. 同期のループを止める

動かされた側が `scroll` を発火し、それが相手を動かし返すと往復が止まらない。

**自分が書いた値を覚えておき、返ってきたイベントの `scrollTop` がそれと
一致したら無視する。**

```
相手の scrollTop に書く → 直後に読み戻した値を expected に記録
相手の scroll が来る → scrollTop が expected と一致（1px未満の差）なら
                        expected を消して何もしない。違えば利用者の操作
```

**読み戻した値を記録する**のが要点。要求した値が範囲外なら
ブラウザが端で丸めるので、要求値と比べると「利用者が動かした」と誤判定して
端で振動する。読み戻せば丸めた後の値と比べられる。

フラグを立てて `requestAnimationFrame` で下ろす形は採らない。`scroll` の発火と
rAFのコールバックの前後関係は1フレームの中で保証されておらず、
**タイミングに依存する**。値の比較なら順序に依らない。

### 5. 計測のタイミング — スクロールするまで測らない

400節の文書での実測（幅1440px、アンカー400件）:

| 段階 | 時間 |
|---|---|
| ミラーのHTMLの組み立て（31.3 kB） | 0.5ms |
| `innerHTML` への反映 | 0.6ms |
| ミラーの400件の `offsetTop` 読み出し | 17.4ms |
| プレビューの800要素の座標読み出し | 2.2ms |
| 合計 | **約20ms** |

打鍵のたびにこれを払うと、N1（1文字あたり50ms以内。現状29.2ms）を食う。
そこで**測るのはスクロールが来たとき**にする。

- 次の場合に「測り直しが要る」印を立てるだけにする: `source` が変わった、
  プレビューのHTMLが変わった、`.editor-wrap` か `.preview` の大きさが変わった
  （`ResizeObserver`）、`document.fonts.ready` が解決した（KaTeXのフォントが
  届くとプレビューの高さが変わる）。
- 印が立っているときの最初の `scroll` で測り直し、以降のスクロールは
  測った結果を使う。**スクロールしなければ計測のコストは0**。

### 6. 触らないもの

- **カーソルと選択範囲**。逆方向の同期で動かすのは `scrollTop` だけ。
- **保存**。位置は保存しない（[0058](../issues/0058-restore-position.md)）。
  スクロールしても「保存中…」は出ない。
- **狭い画面での扱いを分けない。** 幅1199px以下は上下分割になるが、
  スクロールする要素は同じ2つなので、同じ仕組みがそのまま効く。

## 未確認の前提

**この版を書く前に実測して確かめたもの**（`tmp/scratch/` のスクリプトで実行）:

- `marked.lexer()` のトークンの `raw` を連結すると、入力と**完全に一致する**
  （見出し・段落・箇条書き・表・引用・コードフェンス・生HTMLを含む文書で確認）。
  オフセットの積み上げが正確にできる。
- トークンごとに `marked.parser([token])` した結果の連結が、文書全体を
  `marked.parse()` した結果と一致する。
- 先頭の開始タグへの属性の差し込みは `h1` / `p` / `ul` / `table` /
  `blockquote` / `pre` / `details` のすべてで成功し、`li` と `td` には付かない。
- DOMPurify（現在の `USE_PROFILES` の設定のまま）は `data-line` を落とさない。
- **ミラーの折り返しはtextareaと一致する。** CJKの折り返しと分割できない
  長い英単語を含む30節の文書で、textareaの `scrollHeight` 6457px に対し
  ミラーも6457px（差0px、幅1440px）。アンカー間の距離も行高×行数と一致した。
- 計測のコスト（400節）は上の表のとおり約20ms。

**まだ確かめていないもの**（実装はここから始める。崩れたら仕様へ戻る）:

- 幅1199px以下の**上下分割**でも同じ仕組みが成り立つこと。ペインが低くなり、
  画面に入るアンカーが数件になる。
- `document.fonts.ready` の1回の無効化で、KaTeXのフォント差し替えによる
  プレビューの高さの変化を拾い切れること。
- **トラックパッドの慣性スクロールでループが起きないこと。** ヘッドレス
  Chromiumでは慣性を再現できないので、ここは**手元のブラウザで見る**と決める
  （検証スクリプトには載せない）。
- 既存の `find` 区分44件（`.editor-highlights` が同じ `.editor-wrap` に
  重なる）に影響しないこと。

## 検討したが採らなかった案

- **割合（スクロール量の比）で合わせる。** 実装は10行で済むが、実測で最大251px
  （約9行）ずれる。いちばんよく使う書き方（数式・表）がいちばんずれるので、
  「探さずに済む」という目的を満たさない。ただし**アンカーが0件のときの
  落としどころ**としては残す（`mapScroll` の組0件の場合）。
- **アンカーを全行に置く。** 対応は最も正確になるが、400節の文書でspanが
  1600個になり、計測のコストが約4倍になる。ブロック単位で足りる。
- **行番号を介して2段階で写す**（エディタy → 行 → プレビューy）。組にして
  しまえば1段階で済み、逆方向も同じ関数で書ける。行番号は突き合わせの鍵だけに使う。
- **ループ止めをフラグ＋`requestAnimationFrame` で行う。** `scroll` の発火と
  rAFの前後関係が1フレーム内で保証されず、タイミングに依存する。
- **ループ止めを「最後に操作したペイン」で行う**（`wheel` や `pointerdown` で
  主導権を決める）。入力の種類を数え上げることになり、キーボード・
  スクロールバーのドラッグ・`scrollIntoView` など漏れが増える。
- **ミラーをReactで描く。** 31KBの文字列を打鍵のたびに `dangerouslySetInnerHTML`
  へ渡すことになる。ミラーはUIではなく測定用なので、計測のときだけ組み立てる。
- **プレビューのスクロールでカーソルも動かす。** 読み返している最中に編集位置を
  失う。Ctrl+Zの起点も動く。

  0020の土台になる。
