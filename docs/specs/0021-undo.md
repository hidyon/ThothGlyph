# 0021: パレットで挿入したあとUndoで戻せない

- 対応issue: [0021](../issues/0021-undo.md)
- 状態: implemented
- 作成日: 2026-09-20

## 目的

いまはパレットの記号を押すと、ブラウザのUndo履歴が切れる。押し間違えた記号を
Ctrl+Zで1手で取り消せず、手で消すしかない。実測（現行の開発サーバ）でも
`x+1` と打ってから「分数」を押すと `x+1\frac{}{}` になり、
**Ctrl+Zを押しても値が1文字も変わらない**。

このissueを解決すると、パレットからの挿入が手で打った文字と同じ履歴に乗る。
押し間違えたらCtrl+Zで戻せて、Ctrl+Shift+Z（Ctrl+Y）でやり直せる。
アプリ独自のUndoスタックは持たない。

## 仕様

### 挿入の実行方法を変える

いまは挿入後の全文を計算して `setSource` で差し替えている。これをやめ、
**textarea に対して `document.execCommand('insertText', …)` で入れる**。
ブラウザ自身の編集操作になるので、ネイティブのUndo履歴に乗る。

`execCommand` は非推奨APIだが、**textareaのUndo履歴を保ったまま文字を入れる
手段は他にない**（「検討したが採らなかった案」に実測を載せる）。

挿入の手順を次の順で固定する。

```
1. textarea.focus()
2. textarea.setSelectionRange(range.start, range.end)   ← 直前の打鍵とUndo単位を切る
3. document.execCommand('insertText', false, inserted)
4. textarea.setSelectionRange(cursor, cursor)           ← 直後の打鍵とUndo単位を切り、カーソルを置く
```

**2と4の `setSelectionRange` は、カーソルを動かすためだけのものではない。**
Chromiumは連続した入力を1つのUndo単位にまとめるため、これを挟まないと
「打つ→挿入→打つ」が**まとめて1回で消える**。実測（HeadlessChrome 153、素のtextarea）:

| 挿入前後に `setSelectionRange` | `aaa` 打鍵 → `INS` 挿入 → `bbb` 打鍵 のあとCtrl+Zを繰り返した値 |
|---|---|
| 呼ばない | `""`（1回で全部消える） |
| 呼ぶ | `aaabbb` → `aaa` → `""`（順番どおり） |

3で発生する `input` イベントは `isTrusted: true`・`inputType: 'insertText'` なので、
`Editor` の `onChange` がそのまま発火し、`source` state は通常の入力と同じ経路で
更新される。**React state を唯一の正とする構造は変えない**（DOMが先に変わり、
`onChange` 経由で state が追いつく形になる）。Undo/Redoのときも
`inputType: 'historyUndo' / 'historyRedo'` の `input` イベントが出るので、
state もプレビューも追随する。

### 失敗したときの退避

`execCommand` が `false` を返す、または例外を投げる、あるいは
`textareaRef.current` が `null` のときは、**現在の実装（`setSource` で全文差し替え＋
`requestAnimationFrame` でカーソル復元）にそのまま落ちる**。挿入自体が効かなく
なるのは回帰なので、Undoが効かない状態に留めるほうを選ぶ。

### `insertSnippet` の戻り値を増やす

`execCommand` は「どの範囲を何で置き換えるか」で指定する。いまの
`insertSnippet` は挿入後の全文しか返さないので、**置き換える範囲と入れる文字列**を
足す。計算の規則そのものは0009から変えない。

```ts
export type InsertResult = {
  text: string      // 挿入後の全文（退避経路と単体テストで使う）
  cursor: number    // 挿入後にカーソルを置く位置
  start: number     // 置き換える範囲の始まり
  end: number       // 置き換える範囲の終わり
  inserted: string  // その範囲に入れる文字列
}
```

不変条件は `text === source.slice(0, start) + inserted + source.slice(end)`。
単体テストでこれを固定する。

入出力の例（`CURSOR_TOKEN` は `|` で表す）:

| source | snippet | 選択 | start | end | inserted | text |
|---|---|---|---|---|---|---|
| `x+1` | `\alpha`（トークンなし） | なし（カーソル3） | 3 | 3 | `\alpha` | `x+1\alpha` |
| `x+1` | `\alpha`（トークンなし） | `x+1`（0–3） | 3 | 3 | `\alpha` | `x+1\alpha` |
| `x+1` | `\sqrt{\|}` | `x+1`（0–3） | 0 | 3 | `\sqrt{x+1}` | `\sqrt{x+1}` |

2行目が「選択を置き換えずに直後へ入れる」（0009）で、範囲が `[3,3)` の空範囲に
なることがこの表から分かる。

### 対象ファイル

| ファイル | すること |
|---|---|
| `src/lib/insertSnippet.ts` | 戻り値に `start` / `end` / `inserted` を足す。計算の規則は変えない |

READMEのスクリーンショットも撮り直さない。

## 未確認の前提

- **React 19 の制御された textarea が、`execCommand` の `input` を `onChange` で
  拾うこと。** 実測したのは素のtextareaだけで、Reactを通した経路は未確認。
- **手順4の `setSelectionRange` が、その後のReactの再描画で巻き戻らないこと。**
  `value` が一致していればReactはDOMを触らないはずだが、未確認。
- **Chromium以外での挙動。** この環境で確かめられるのはChromiumだけなので、
  受け入れ基準もChromiumで見る。Firefox・SafariもtextareaでのinsertTextに
  対応しているが、**ここでは確かめない**。退避経路があるので、効かない環境でも
  挿入自体は動く。

## 実装中に崩れた前提（2026-09-20）

**打鍵のUndoの粒度が、素のtextareaと実アプリで違った。**
仕様を書くときの実測（素のtextareaに対するプローブ）では、連続して打った
`aaa` が1つのUndo単位にまとまっていた。それを根拠に受け入れ基準へ
「Ctrl+Zを3回押すと3段で戻る」と書いたが、**実アプリで測ると打った文字は
1文字ずつ1段**だった（`aaa\alpha bbb` から10回押した実測）。

```
aaa\alpha bbb → aaa\alpha bb → aaa\alpha b → aaa\alpha  → aaa → aa → a → ""
                                                    ↑ 挿入はここで1回でまとまって消える
```

**このissueの目的（挿入が1手で取り消せる・順番どおりに戻る）は満たしている。**
外れたのは回数の見積もりだけなので、受け入れ基準を実測の形へ直した（上記）。
打鍵側をまとめるにはブラウザのネイティブな挙動へ介入することになり、
issueの「やらないこと」に近づくので、そこは追わない。

**「保存中…」が消えなくなる既存の不具合を見つけた。**
パレットに触れず、1文字打って即Backspaceで保存済みの内容に戻すだけで再現する。
`App.tsx` の保存のeffectが `source === savedSource.current` で早期に抜けるとき、
直前に立てた `pending` を戻さないため。**0021の変更が起こしたものではない**ので
[0036](../issues/0036-save-status-stuck.md) として起票し、ここでは直さない。
検証スクリプト側は、保存が終わったことをlocalStorageの内容で待ってから
次の手順へ進むことで、この不具合に引っかからないようにした。

## 検討したが採らなかった案

### `textarea.setRangeText()`

非推奨ではなく、範囲を指定して置き換えられる。**しかしUndo履歴に乗らない。**
実測（HeadlessChrome 153、素のtextarea）:

```
aaa と打つ → setRangeText('RNG', 3, 3) → 値 "aaaRNG"
Ctrl+Z → 値 "aaaRNG"（変わらない）
```

同じ手順を `execCommand('insertText')` でやると `aaa` に戻る。目的を果たせない。

### アプリ独自のUndoスタック

issueの「やらないこと」。ブラウザの履歴と二重になり、どちらが効くか
予測できなくなる。今回は**ネイティブの履歴に乗せる**方法が実測で見つかったので、
持つ理由がない。

### `beforeinput` / `InputEvent` を自分で投げる

スクリプトから作ったイベントは `isTrusted: false` で、ブラウザは編集を実行しない。
値を変えるには結局こちらで代入することになり、履歴は切れたままになる。

### EditContext API

`contenteditable` 側の仕組みで、`textarea` には使えない。textareaをやめて
`contenteditable` に移すのは、このissueに対して大きすぎる。

## スコープ外

- **ファイルの読み込み（0012）・書き出し・「サンプルに戻す」のUndo。**
  文書の全文が入れ替わる操作で、1手の挿入とは性質が違う。現状これらの直後に
  Ctrl+Zを押しても何も起きないことは実測済みで、**古い内容が蘇る事故は起きない**。
  戻せるようにするなら [0023](../issues/0023-snapshot-recovery.md)（履歴からの復旧）の側。
- **キーボードショートカット全般**（[0008](../issues/0008-keyboard-shortcuts.md)）。
  Undo/Redoのキーはブラウザのものをそのまま使い、こちらでキーを拾わない。
- **文書をまたぐ履歴**（[0004](../issues/0004-multi-document.md)）。
- **Chromium以外のブラウザでの確認。**
- **「保存中…」が消えなくなる不具合**（[0036](../issues/0036-save-status-stuck.md)）。
  今回見つけたが、0021の変更とは独立した既存の不具合。
