# 0016: プロダクト全体の仕様文書を書く

- 対応issue: [0016](../issues/0016-product-docs.md)
- 状態: implemented
- 作成日: 2026-09-19

## 目的

issue単位の仕様の上に、プロダクト全体を見る4文書を置く。新しく入る開発者が、
コードを読む前に「何を満たすべきか・どう組み立てているか・いま何ができるか・
どう確かめるか」を把握できるようにする。

## 仕様

`docs/` 直下に4ファイルを置く。読み手は**このリポジトリに新しく入る開発者**
（将来の自分とClaudeを含む）。

| ファイル | 書くこと | 書かないこと |
|---|---|---|
| `requirements.md` | 誰の何のための道具か、満たすべき要求、非機能要求（性能・可用性の数値）、明示的に扱わないこと | 実装方法、画面の詳細 |
| `architecture.md` | 全体の構成、変換パイプライン、状態の持ち方、保存形式、依存とその理由、守るべき制約（順序・約束） | 個々の関数の使い方 |
| `functional-spec.md` | いま何ができるか。画面の構成、各機能の振る舞い、入力形式（数式記法）、エラー時の見え方 | 未実装の機能（issue番号だけ添える） |
| `test-spec.md` | 何をどう確かめるか。単体テストと実機検証の分担、現在のテスト一覧、検証の手順、追加するときの指針 | 個々のテストのコード |

### 共通の約束

- **現在の実装を正として書く。** 未実装は「今はない（[NNNN](...)）」と添えるだけ。
- 数値（数式の件数、性能の実測値など）は実測に基づく。推定を書かない。
- 相互にリンクする。同じことを2か所に書かない（重複は乖離の元）。
- 各文書の冒頭に、更新すべきタイミングを1行で書く。

### issue仕様との役割分担

`docs/specs/NNNN-*.md` は**変更の単位**（この変更で何がどう変わるか、受け入れ基準）。
4文書は**現在の姿**。issueをクローズしたとき、4文書の記述が変わるなら同じ
コミットで直す。CLAUDE.mdの「検証する」フェーズにこの1行を足す。

### 対象ファイル

| ファイル | 変更内容 |
|---|---|
| `docs/requirements.md` | 新規 |
| `docs/architecture.md` | 新規 |
| `docs/functional-spec.md` | 新規 |
| `docs/test-spec.md` | 新規 |
| `CLAUDE.md` | 構成図に4文書を追加。クローズ時に4文書を見直す1行 |

## 未確認の前提

- なし（新規の文書のみで、ライブラリや環境に依存する判断がない）。

## 受け入れ基準

- [x] `docs/` に4文書があり、それぞれ冒頭に更新のタイミングが書かれている
- [x] 文書内に書いた事実（ファイル構成、保存キー、パレットの件数、テスト件数、
      性能の実測値）が、実際のコードと検証結果に一致する
- [x] 未実装の機能が「今はない」とissue番号つきで書かれ、できるかのように
      読めない
- [x] 4文書とCLAUDE.md・issue仕様の役割分担が明示されている
- [x] CLAUDE.mdから4文書に辿れる
- [x] `npm test` / `npm run build` / `npm run lint` が通る（文書のみの変更なので
      壊れないことの確認）

## 検討したが採らなかった案

- **1ファイル（`docs/design.md`）にまとめる。** 見通しはよいが、4つの関心事は
  更新の頻度が違う（機能仕様は毎issue、要求仕様はまれ）。混ぜると差分が読みにくい。
- **`docs/design/` サブディレクトリに置く。** `docs/` 直下が散らからない一方、
  `issues/` `specs/` と並ぶ位置にないと存在に気づかれにくい。
- **未実装の要求も要求仕様に書く。** 全体像は描けるが、文書と実装の差を
  追う責任が増える。差はissueが持っているので二重に持たない。

## スコープ外

- 文書の自動生成、図の作成ツールの導入。
- README.md（利用者向け）の整備。別issueにする価値はあるが、ここでは扱わない。
