# 0007: 長い文書でプレビューが重い

- 対応issue: [0007](../issues/0007-preview-performance.md)
- 状態: implemented
- 作成日: 2026-09-19

## 目的

1打鍵ごとに文書全体を marked と KaTeX にかけ直しているため、長い文書で入力が
追従しない。実測で400節・400数式の文書に5文字打つのに6.0秒（1文字あたり約1.2秒）。

打っている手が止まらないことを最優先にする。プレビューが一瞬遅れて追いつくのは
許容する。

## 仕様

### 1. 数式の描画結果をキャッシュする

`renderMarkdown.ts` に、LaTeX文字列と `displayMode` の組をキーにした
KaTeX出力のキャッシュ（`Map`）を持つ。

- 1文字打っても、文書中の数式のほとんどは前回と同一である。400個の式を
  毎回描き直しているのが重さの主因なので、ここが一番効く。
- 上限を **500件** とし、超えたら挿入順に古いものから捨てる（素朴なFIFO）。
  数式は1つあたり数KBのHTMLなので、500件でも数MB程度に収まる。
- キャッシュはモジュールスコープに置く。`renderMarkdown` の戻り値は
  これまで通り入力だけで決まる（同じ入力なら同じ出力）ので、純粋関数としての
  約束は保たれる。

### 2. プレビューの更新を入力から切り離す

`App.tsx` で `useDeferredValue(source)` を通した値をプレビューの入力にする。

- textareaの表示は即座に更新され、プレビューの再計算はReactが優先度を落として行う。
- 固定のデバウンス時間を置かない。速い端末では待ち時間ゼロ、遅い端末では自動的に
  後回しになる。時間の定数をこちらで決めずに済む。
- プレビューが古い値を表示している間は、プレビューのヘッダに `更新中…` を出す
  （`source !== deferredSource` で判定）。プレビューを薄く見せるなどの装飾はしない。

### 3. 数値目標

400節・400数式の文書（検証スクリプトが生成する）で:

- 20文字を連続入力したときの**1文字あたりの入力反映（textareaの値が更新されるまで）が
  50ms以内**。
- 入力を止めてから**プレビューが追いつくまで1.5秒以内**。

いまの実測（1文字あたり約1200ms）に対する目標であり、余裕を持って置いている。
達成できない場合は、案として残してある「ブロック単位の差分描画」に進むかどうかを
issueに戻って相談する。

| ファイル | 変更内容 |

| `src/lib/renderMarkdown.ts` | KaTeX出力のキャッシュ。上限つきの `Map` と、キャッシュを空にする関数（テスト用） |

## 受け入れ基準

- [x] 400節・400数式の文書で、20文字の連続入力の1文字あたり反映が50ms以内
- [x] 入力を止めてから1.5秒以内にプレビューが追いつく
- [x] プレビューが遅れている間、プレビューのヘッダに `更新中…` が出る
- [x] 追いついたら `更新中…` が消える
- [x] 短い文書（サンプル文書）では `更新中…` が目に見えて残らない
- [x] 同じ数式を2回描いても出力が同じ（キャッシュが結果を変えない）
- [x] 500件を超える数式を含む文書でも、数式が正しく描画される
- [x] `npm test` と `npm run build` と `npm run lint` が通る

## 検討したが採らなかった案

- **固定時間のデバウンス（入力が止まって150msで描く）。** 実装は小さいが、
  遅い端末では足りず速い端末では無駄に待つ。定数を当てにいくことになる。
  `useDeferredValue` なら端末の速さに合わせて勝手に決まる。
- **ブロック単位で差分描画する。** 効果は大きいが、分割の単位（段落？ 行？）と
  キャッシュの無効化を自前で管理することになる。まず数式キャッシュでどこまで
  届くかを測ってから判断する。
- **Web Workerでレンダリングする。** メインスレッドは空くが、HTML文字列の
  やり取りと非同期化でコードが増える。上の2つで目標に届くなら要らない。
- **仮想スクロール。** プレビュー全体のHTML生成自体が重いので、表示領域を
  絞っても生成コストは減らない。

## スコープ外

- 初期ロードのバンドルサイズ（561kB）の削減。別issueにする価値はあるが、
  ここでは触らない。
- エディタ側（textarea）の描画性能。素のtextareaなので現状で問題はない。

## 実測（2026-09-19、実装後）

| 指標 | 目標 | 実測 | 実装前 |
|---|---|---|---|
| 入力反映（1文字あたり） | 50ms以内 | 29.2ms | 約1200ms |
| 入力停止からプレビュー追随 | 1.5秒以内 | 308ms | — |

400節・400数式の文書で、自動保存が動く状態のまま測った。
